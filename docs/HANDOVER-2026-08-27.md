## 2. The headline result

**Wan2.1 T2V 1.3B generates real text-to-video on free Kaggle T4 x2**, about
**49 minutes** per 5-second clip (measured; the earlier ~10 min figure was at
50 frames, from a run the grey-clip bug invalidated).

This reverses the 2026-08-23 conclusion. The earlier failures were a *loading
strategy*, not a hardware limit:

| | Text encoder | Transformer | Peak |
|---|---:|---:|---:|
| Old (5 configs, all failed) | 22.7 GB | 2.8 GB | ~25 GB together |
| Phase 1 | 22.7 GB on CPU | — | 22.7 GB |
| Phase 2 | — | 2.8 GB on GPU | **~4 GB** |

The encoder runs once, then is freed. `WanPipeline` accepts `prompt_embeds`
instead of `prompt`, so the two never coexist. Full detail and the two bugs
found along the way:
`docs/evidence/EXP-005_KAGGLE_T2V_WORKING_2026-08-27.md`.

**The full run landed 2026-08-27.** `exp005-t2v-20260827T104718Z`, ledger
entry `EVD-EXP005-011`: 4/4 clips, 4 distinct digests, 832x480, 81 frames,
5.06 s each, H.264, peak 12.45 GiB VRAM and 29.13 GiB RAM of 31.35 available.
Verified independently off Kaggle by parsing the containers.

**Still not established: quality.** The run is *scoreable* but has not been
scored. `QUALITY_SCORECARD.md` names the run and stays otherwise empty until
both reviewers fill it blind.

**The cost of that run:** 2901.9–2952.1 s per clip, mean 2918.8 s, 3.24 GPU-
hours for four clips. At ~30 free GPU-hours a week that is **~37 clips per
week for the whole team**, and it is 62% over `PB-FRAMEPACK-LATENCY` (1800 s)
— a budget written for the local path, so the contract has no Kaggle T2V
latency budget at all. One should be written before W3. The lever is clip
length: 50 frames ran at ~10 min, 81 frames at ~49 min.

## 4. What shipped this week

### Profile: gender and birthday *(committed)*

- `supabase/012_add_user_profile_fields.sql`, **already applied to the live
  database** on 2026-08-19. Local SQLite self-migrates.
- Profile screen leads with username; email moved into the detail block;
  Gender and Birthday rows render `--` when unanswered.
- Edit form: three-chip gender selector (re-tap to clear), date picker with a
  UTC-pinned conversion, both optional.
- **Wire contract detail worth knowing:** empty string clears, absent means
  leave alone. `explicitNulls = false` drops nulls from the body, and
  `encodeDefaults = false` drops any field still equal to its default — so
  `gender`/`birthday` have **no default values** in `MeUpdateRequest`. Removing
  that is a silent regression; `MeUpdateRequestSerializationTest` pins it.

### Email sync *(committed)*

The verified JWT's email claim is now written through to `users.email` when it
differs. Previously read and discarded, so profiles showed whatever the signup
trigger seeded. Role and disabled state still come from the row, never a claim.

Also added: first-sign-in provisioning for the **SQLite mirror only**, which
has no Supabase signup trigger. Postgres keeps the 401.

### Error envelope surfacing *(committed)*

`HttpException.toAppError()` now parses `{"error": {"code", "message"}}`.
Previously discarded, so a taken username reached the user as
"Request failed with HTTP 409". 5xx deliberately keeps a generic line.

### W4 — reference images reach providers *(committed)*

`del image_path` removed. `StorageBackend.read_image_bytes()` added to both
backends; providers resolve the upload and pan across the account's own image
instead of a generated still. Type comes from **magic bytes**, not a
client-declared header. Every failure degrades to the text path.

### Live Supabase *(done, config not committed — `.env` is gitignored)*

`CRETONA_DATABASE_BACKEND=postgres`, `CRETONA_STORAGE_BACKEND=supabase`.
Verified: Postgres round-trip on the new columns, Storage upload → signed URL
→ fetch → delete. `CRETONA_SUPABASE_JWT_ISSUER` was empty and is now set.

Run the live backend with:

```
scripts\run-fastapi.ps1 -SkipPreflight
```

**`-SkipPreflight` matters.** Without it the profiler runs with `--auto-tune`
and rewrites `CRETONA_DEFAULT_VIDEO_PROVIDER` in `.env` from GPU/RAM on every
start, silently overriding whatever you set.

## 5. The bake-off notebook

`docs/experiments/EXP-005/EXP-005_T2V_bakeoff.ipynb` — 29 cells, sections 1-13.
Since 2026-08-27 it generates **one clip per cell** (cells 16-19), so an
interrupt costs one clip rather than the whole set. `results.json` is rewritten
after each.
Generated by `build_bakeoff_notebook.py`; **edit the builder, not the JSON**,
then re-run it.

Operating instructions: `docs/experiments/EXP-005/RUNBOOK.md`.

Three checkpoints make retrying cheap:

| Checkpoint | Saves |
|---|---|
| `SMOKE_TEST = True` (default) | ~3 min instead of ~3.3 h |
| Embeddings cached to disk | ~5 min of encoder loading per retry |
| Existing clips skipped | ~49 min per clip already made |

**Smoke mode makes 2 clips, not 1** — both prompts, one seed. So
`distinct outputs: 2/2` is correct there; a full run gives `4/4`.

### Two bugs the harness now catches

**Grey clips.** `encoder.embed_tokens.weight | MISSING | newly initialized` in
the UMT5 load report meant the tie to `shared.weight` was not applied, so every
token embedded to noise and the model denoised to flat grey — identical for
every prompt. The notebook now re-points that weight after loading.

**A metric that lied.** The self-test comparing two prompts reported
`0.001976`, which looked like failure. Only 120 of 226 token positions carry
content; averaging over 106 identical padding rows drags the mean to near zero.
Measured on content only: `mean |diff| 0.073210`, **cosine 0.153194** — healthy.
The test now excludes padding and gates on `cosine > 0.999`.

**And an invalid run that reported success.** Four files that were two videos
previously logged `4/4 clips generated`, `status: "passed"`. Cell 25 now
compares output digests, prints a NOT-scoreable warning, and records `failed`.

### Corrections to carry forward

- The worker plan's §4 W3 names HunyuanVideo 1.5. **Use Wan2.1 T2V 1.3B** —
  Hunyuan's transformer alone is ~16.6 GB in fp16, above a single T4, and the
  two-phase split does not rescue it.
- A live worker must keep the encoder **resident between jobs**. Re-running
  phase 1 per request would cost ~5 minutes each time.
- **The lease must be renewed on a timer.** `poll_lease_seconds` defaults to
  120 with a ceiling of 3600 (`backend/app/config.py`). A 2918 s job at the
  default is re-claimed about 24 times; even the ceiling leaves ~11 minutes of
  margin over the slowest clip. This is a correctness bug waiting in W3, not a
  tuning question.
- `FREE-LOCAL-BEST-OUTPUT.md` §3 ranks candidates by VRAM alone. RAM and total
  pipeline size are what actually decide. A parameter count in a model name
  describes the transformer, not the pipeline — Wan2.1 "1.3B" downloads 28.4 GB.
