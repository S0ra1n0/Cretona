## 2. Environment

Python **3.12+** is required (`pyproject.toml` sets `requires-python`). The
Microsoft Store 3.11 will not work.

```
python -m venv backend-fastapi\.venv
backend-fastapi\.venv\Scripts\python.exe -m pip install -c backend-fastapi\constraints-windows-py312.lock -e "backend-fastapi[dev]"
```

The lock is authoritative. If you add a dependency, regenerate it in the same
commit — `pyproject.toml` and the lock disagreeing has already broken this repo
once (`3320798`), and the symptom was pytest failing to collect at all, which
made every "N tests passed" claim on the branch unreproducible.

**Postgres tests** need a disposable local database:

```
docker run -d --name cretona-pg -e POSTGRES_PASSWORD=localdevonly -e POSTGRES_DB=cretona -p 55432:5432 postgres:16-alpine
```

```
$env:CRETONA_TEST_DATABASE_URL='postgresql://postgres:localdevonly@127.0.0.1:55432/cretona'
```

> **`CRETONA_TEST_DATABASE_URL` must never point at Supabase.** The fixture
> drops and recreates tables. `tests/db_safety.py` refuses non-local hosts, and
> that guard exists because the hazard was shipped before it was noticed.

**Gates**, from the repo root:

```
backend-fastapi\.venv\Scripts\python.exe -m ruff check backend-fastapi
backend-fastapi\.venv\Scripts\python.exe -m pytest backend-fastapi
```

without. Ruff clean. One pre-existing Starlette/httpx deprecation warning.

## 3. What is actually proven

This is the section to trust. Everything else in the repo's docs describes
intent.

### Proven against live Supabase on 2026-08-15

- Server boots against live Postgres; schema validated for migrations 002–008.
- Unauthenticated requests are refused (`401 UNAUTHENTICATED`).
- **A real Supabase-issued ES256 token authenticates end to end**: signature
  verified from the project's JWKS, `sub` resolved to a `public.users` row,
  role read from the database, quota computed from `video_projects`.
- Migrations 002–008 are all applied. Verify with:
  `backend-fastapi\.venv\Scripts\python.exe scripts\live-supabase-migration-gate.py verify-008 --env-file backend\.env`

- **Supabase Storage.** Every storage test uses a mock HTTP transport. No
  object has been uploaded, signed, or deleted against a real bucket. The

  verification was reads plus a local container.

  They were deliberately disabled for the verification run.
- **`AdminScreen.kt`** — 655 lines of composables, unreviewed. Its ViewModel
  and navigation were reviewed; the rendering was not.
- **A real video provider.** `FakeVideoProvider` proves workflow only.
  `RealAiVideoProvider` and `Wan21VideoProvider` are adapters, not evidence.

## 4. The ES256 incident — read this one

TASK A shipped a Supabase JWT verifier in August with 24 passing tests and an
acceptance criterion of "valid Bearer token → correct canonical identity".

**It could never authenticate a real user of this project.** The verifier hard-
pinned HS256; the project signs **ES256**. Every passing test used a token
minted locally with the wrong algorithm. Roughly three months of work sat on an
auth layer that did not function.

Nothing found it except running the service against the real thing. Not more
tests. Not review. The roadmap even recorded "HS256 settled" because the
question was asked and answered from memory rather than checked.

Fixed in `1ec5a49`: both schemes are supported, selected by
`CRETONA_SUPABASE_JWT_ALGORITHM`, never inferred from the token. Public keys
come from the project's JWKS endpoint, cached, refetched on an unknown `kid`
with a 30s floor so an unauthenticated endpoint cannot be turned into a request
amplifier.

**The lesson to carry:** a green suite tells you the code does what its author
expected. It says nothing about whether the expectation matched reality.

## 5. State of `backend-fastapi\.env`

Untracked, machine-local, and currently configured for verification rather than
normal running. **Before doing anything else, revert these two:**

```
CRETONA_POLLER_ENABLED=true
CRETONA_GENERATION_LOG_RETENTION_ENABLED=true
```

They were set to `false` because on startup the poller claims in-flight
projects from live and advances them with the fake provider, and the retention
worker runs a `DELETE` before its first sleep. Both are correct behaviours that
you do not want firing during a read-only check.

Current working configuration:

```
CRETONA_ENVIRONMENT=production
CRETONA_AUTH_MODE=supabase
CRETONA_SUPABASE_JWT_ALGORITHM=ES256
CRETONA_SUPABASE_URL=https://<project-ref>.supabase.co
CRETONA_DATABASE_BACKEND=postgres
CRETONA_DATABASE_URL=<the DIRECT_URL value from backend\.env>
CRETONA_STORAGE_BACKEND=local        # not yet switched to supabase
```

Use `DIRECT_URL`, not `DATABASE_URL`. psycopg uses prepared statements, which
Supabase's transaction pooler does not support; the failures are intermittent
and look random.

## 8. Known hazards

- **`supabase/seed_dev_users.sql:58-59` contains working passwords in git.**
  They no longer match the live accounts, but the pattern is committed
  credentials for an account named `admin@`. Rotate and stop committing them
  before this project holds anything real.
- **Webhook replay is not addressed.** `POST /webhooks/{provider}` verifies an
  HMAC signature but has no timestamp or nonce, so a captured webhook can be
  replayed. Fine while no provider posts webhooks; not fine afterwards.
- **Rate limiting is Postgres-backed but the audit write is not transactional.**
  A failed audit row is logged and swallowed, so an admin action can succeed
  with no audit trail. Correct fix is one transaction shared with the mutation.
- **The migration gate defaults to a root `env` file that does not exist.**
  Pass `--env-file backend\.env`.
- **The gate only knows migrations 006–008.** Anything earlier or later is
  applied by hand without its hash pinning or project-identity check.

## 9. Rules inherited from the original handover

Still in force:

- Model calls go through FastAPI. The Express backend in `backend/` is
  migration evidence, not a runtime.
- Android stays provider-neutral; raw model ids stay server-side.
- No model weights, caches, output video, or secrets in Git.
- No destructive migration against remote Supabase. Prepare and evaluate
  first; applying needs an explicit decision.
- Never present `FakeVideoProvider` output as AI-generated video.
