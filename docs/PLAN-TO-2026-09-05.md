### D1 — RESOLVED: three generation modes

**Decision: the app supports `text`, `image`, and `text+image`.** Contract in
`API_CONTRACT.md` Part II §5. The client sends `prompt`, `imagePath`, or both;
the server derives the mode and returns it. At least one is required.

**Lecturer scope, confirmed by Bruce:** no specific model or requirement that
the uploaded image must drive the output. Therefore text-to-video is the
release-critical mode; image-conditioned model research is optional unless the
team chooses to make it a demo claim.

This is cheap in the app and API, and expensive in the model layer:

| Layer | Cost | Status |
|---|---|---|
| Android — optional prompt, image-only submit | ~2 hours | do it |
| API — nullable `prompt`, derived `mode`, validation | ~2 hours | do it |
| Provider routing by mode | ~2 hours | do it |
| **A model that actually conditions on the image** | **unknown** | **the risk** |

Wan2.1 T2V 1.3B is text-only. Nothing currently in the project does image-to-video
on a T4: Wan2.1's I2V variant is 14B, HunyuanVideo's transformer alone is ~16.6 GB,
and FramePack F1 has never been run anywhere.

**Rule, from the contract:** `image` and `text_image` must never silently fall
back to text-only. A user who supplies an image and gets a video that ignores it
has been misled, and a grader will notice. Until an image-capable provider is
proven, those modes return `PROVIDER_ERROR`.

**Optional timeboxed spike, after S-14, hard stop at 3 hours.** Candidates
in order: **LTX-Video 2B** (does both T2V and I2V, distilled for few-step
inference, so it may also solve D2), then **Stable Video Diffusion** (~2.5 GB,
image-only, comfortably fits a T4). If neither works by the stop, ship `text`
only and record the other two modes as a disconfirmed result — that is a
legitimate outcome and the evidence ledger already has the pattern for it.

### D2 — RESOLVED: 65 frames, 30 steps, and four other levers

**Decision: 65 frames (4.06 s at 16 fps, 4n+1) and 30 steps, not 81 and 50.**

Why it is slow, in order of contribution:

1. **50 sequential denoising steps.** Each is a full forward pass. Nothing about
   diffusion is parallel across steps — this is a 50x multiplier on everything.
2. **Full 3D attention.** 21 latent frames x 30 x 52 patches ~= 32,760 tokens,
   and attention is O(N^2). Token count scales with frames, so frame count hits
   the quadratic term.
3. **A T4 is a 2018 card.** ~65 TFLOPS fp16, no bf16 acceleration, and the
   `sage_hub` fast-attention backend is unavailable, so it runs a slower kernel.
4. **Only one of the two GPUs is used.** Phase 2 does a plain `.to("cuda")`.
5. **RAM at 93%.** 29.13 of 31.35 GiB at 81 frames. Some of the 4.7x jump from
   49 to 81 frames is probably paging, not compute — no clean attention model
   fits both measured points.

Levers, ranked by (confidence x win) / effort:

| Lever | Expected | Confidence | Effort |
|---|---|---|---|
| **Steps 50 -> 30** | **1.7x** | high — linear, guaranteed | trivial |
| **Frames 81 -> 65** | **~1.8x** | medium — interpolated | trivial |
| **Both T4s, one clip each** | **2x throughput** | high | half a day in W3 |
| `torch.compile` on the transformer | 1.2-1.4x | medium | low, amortised in a resident worker |
| TeaCache / step caching | 1.5-2x | medium, costs some quality | half a day |
| Lower resolution 832x480 -> 640x384 | ~1.6x | high | trivial, but off the trained resolution — quality cost |
| A faster model (LTX-Video 2B, distilled) | potentially 5x+ | low | an optional post-S-14 spike can answer this |
| fp8 quantisation | — | n/a | T4 has no fp8. Do not try |

**Target: ~15 min per 4-second clip** from steps and frames alone, roughly 2x
that in throughput once both cards are used. **Measure one clip before W3 is
built on the number** — 65 frames is interpolated, not measured.

Also resolve: `schemas.py` accepts `durationSeconds` 2-10, default 5. If every
clip is 4.06 s the app is offering a choice it cannot honour. Either pin the app
to one duration or map the range onto frame counts.

-- Append-only ledger. The balance column above is a cache; this is the truth.

  on public.credit_transactions (user_id, idempotency_key)
  where idempotency_key is not null;
create index idx_credit_tx_user_created
  on public.credit_transactions (user_id, created_at desc, id desc);

create table public.credit_packages (
  id          uuid primary key,
  name        text not null,
  credits     integer not null check (credits > 0),
  price_vnd   integer not null check (price_vnd >= 0),
  is_active   boolean not null default true,
  sort_order  integer not null default 0,
  created_at  timestamptz not null default now()
);

create table public.payments (
  id              uuid primary key,
  user_id         uuid not null references public.users (id) on delete cascade,
  package_id      uuid not null references public.credit_packages (id),
  amount_vnd      integer not null,
  credits_granted integer not null,

  status          text not null check (status in ('pending','completed','failed')),
  idempotency_key text,
  created_at      timestamptz not null default now(),

);
create unique index uq_payments_idem
  on public.payments (user_id, idempotency_key)
  where idempotency_key is not null;

create table public.events (
  id                 uuid primary key,
  code               text not null unique,
  name               text not null,
  description        text,
  kind               text not null check (kind in ('grant','discount')),
  bonus_credits      integer check (bonus_credits > 0),      -- kind = grant
  discount_percent   integer check (discount_percent between 1 and 100),
  recurrence         text not null check (recurrence in ('once','daily','weekly')),
  active_days        text,        -- 'sat,sun' when recurrence = weekly
  active_from_minute integer,     -- 1200 = 20:00 local (UTC+7)
  active_to_minute   integer,     -- 1320 = 22:00 local
  starts_at          timestamptz not null,
  ends_at            timestamptz not null,
  max_claims         integer,     -- null = uncapped

  is_active          boolean not null default true,
  created_at         timestamptz not null default now(),

-- The unique index is what makes "one claim per weekend" true under a double-tap.
create table public.event_claims (
  id              uuid primary key,
  event_id        uuid not null references public.events (id) on delete cascade,
  user_id         uuid not null references public.users (id) on delete cascade,
  period_key      text not null default '',
  credits_granted integer not null,
  created_at      timestamptz not null default now(),
  unique (event_id, user_id, period_key)
);

create table public.settings (
  key        text primary key,
  value      text not null,

  updated_at timestamptz not null default now()
);

Seed `settings` with `generation_cost_credits = 1` and
`generation_cost_credits_long = 2`, plus three credit packages.

### The invariants that must hold

- **The ledger is append-only.** Never update or delete a `credit_transactions`
  row. `users.credit_balance` is a cache written in the same transaction;
  `balance_after` exists so drift is detectable.
- **Every mutation goes through one service.** `CreditService` is the only
  writer. No route, no admin handler, and no provider touches the balance.
- **Charge is idempotent.** Reuse `Idempotency-Key` — the same key from a
  retried submit must not charge twice. The unique partial index enforces it
  in the database, not just in Python.
- **The registration cap is enforced in SQL**, not by reading a count and then
  inserting. `insert ... select ... where (select count(*) ...) < max` or a
  row lock; a read-then-write race gives away more bonus credits than the
  campaign allows.
- **Users cannot write their own balance.** Already true structurally: no
  client-supplied field reaches it.

### Charge policy

**Reserve at submit, refund on failure.** The brief permits either
("không trừ Credit **hoặc** phải tự động hoàn lại"), and reserving is the only
option that stops a user with one credit launching ten jobs.

- Submit → `-cost`, reason `generation`, `ref_id = project_id`
- Failure or cancel → `+cost`, reason `refund`, same `ref_id`
- Insufficient balance → `402` with an error code the app maps to
  "buy more credits", not the current `429 QUOTA_EXCEEDED`

`QuotaService` stays as it is. It is now defence in depth rather than the
budget control, and `ADR-007` gets a one-paragraph amendment saying so.
