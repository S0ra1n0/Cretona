## 3. What changed this session

### Authentication (new)
The app had **no login at all** — `NetworkModule` attached a hardcoded
`X-Debug-User-Id` and a fake HS256 token to every request, so everyone was the
same fixed identity forever.

Now: a galaxy-gradient login screen calling Supabase Auth directly
(`POST /auth/v1/token`, ADR-002). On success the token goes into an in-memory
`SessionManager` and the app sends *only* that token. With no session it falls
back to the dev identity, so credential-free local testing still works.

`SessionManager` is memory-only by design — every cold start returns to login.
Persisting sessions is unimplemented, not overlooked.

### Navigation shell (new)
`MainScreen` hosts three tabs behind one gradient app bar and a bottom bar:

- **Home** — the create form (its old "Recent projects" list was removed)
- **History** — past projects, newest/oldest sort, date headers
- **Profile** — avatar, email, role, quota, edit, sign out

Tabs share one `HomeViewModel` (Hilt scopes it to the destination), so
switching tabs does not refetch. `Admin` remains a separate destination.

### Profile setup (new)
Shown after login when the account has **no username** — a new account's state.
Avatar via `PickVisualMedia` (no storage permission), username validated
min 3 / max 25 / `[A-Za-z0-9_]` in both app and backend.

The same composable serves editing from the Profile tab, so the rules and the
upload-then-save ordering cannot drift between the two paths.

### Avatar support (new backend feature)
The avatar had **zero backend support** — no column, no field, no migration.
Added: `supabase/010_add_user_avatar.sql`, `users.avatar_path`, `avatarPath` on
`PATCH /me`, `avatarUrl` on `MeResponse`.

Stores the **object key, never a signed URL** — a stored signed URL is a broken
image within the hour. The URL is minted per response, as `videoUrl` already is.

### Earlier in the session
Migration 009 applied to live; rate limiter cut from 5–6 round trips to 2
(~1.4s → ~800ms, ADR-010 addendum); `API_CONTRACT.md` corrected where it
documented fields the API never returned; `backend-fastapi/` deleted.

## 4. Admin access — how it was verified

Asked to check "every method, not just the UI button". Result:

- All 6 `/admin/*` routes require `AdminId`; verified by script, none unguarded.
- Role is read from the **database**, never a token claim; defaults to `user`.
- Probed live: no credentials → 401; spoofed `X-Debug-User-Id` → 401; spoofed
  header + fabricated role headers → 401; real admin token → 200.
- **Demotion test:** flipped the role to `user` in the DB and retried with the
  *same still-valid token* → immediate **403**. Authority follows the database,
  so revocation is instant.
- No deep links; `MainActivity` is exported only with MAIN/LAUNCHER.

**Gap found and fixed:** only the button was gated, not the route. A 403 from
any admin endpoint now flips `isForbidden` and the screen shows "Admin access
required". Three layers; only the server one is load-bearing.

## 5. Running it

### Dev backend (recommended)

```powershell
.\scripts\run-dev-backend.ps1 -RealAuth
```

SQLite in `backend\.devdata\` — **never touches live**. `-RealAuth` verifies
real Supabase tokens, so login determines identity and admin role works.
Without the flag it uses the fixed dev identity and signing in as somebody else
will *not* change the profile you see. The script prints which mode it is in.

The avatar column auto-adds on SQLite, so no migration is needed here.

### Emulator

```powershell
& "C:\Users\M15R6\AppData\Local\Android\Sdk\emulator\emulator.exe" -avd Pixel_10_Pro
```

Then Android Studio ▶, or:

```powershell
$env:JAVA_HOME = 'C:\Program Files\Android\Android Studio\jbr'
.\gradlew.bat :app:installDebug --no-daemon
```

`local.properties` must point at port **8000** (it had a stale Express-era 3000).

### Live — requires migration 010 first

The backend **refuses to start** against live until 010 is applied, naming the
file. Order matters:

```powershell
# 1. apply (writes to live)
& ".\backend\.venv\Scripts\python.exe" .\scripts\live-supabase-migration-gate.py `
  apply-010 --env-file .\backend\.env --confirm-project-ref fisnwdzhyuiiursljblw

# 2. verify
& ".\backend\.venv\Scripts\python.exe" .\scripts\live-supabase-migration-gate.py `
  verify-010 --env-file .\backend\.env

# 3. run
.\scripts\run-fastapi.ps1
```

Live means real writes and real quota. Only switch when you want the data there.

## 6. Known gaps

1. **Account creation is not implemented.** "Create an account" is a deliberate
   no-op. Profile setup is reachable today only via an account with no username.
2. **Sessions do not persist.** Cold start returns to login.
3. **Pagination is ignored.** The API returns `nextCursor`/`hasMore`; History
   and the admin lists show only the first page.
4. **Destructive admin actions have no confirmation** (promote/demote/disable
   fire on one tap).
5. **`GET /api/v1/health` never touches the database** — the admin panel's
   "Ping Server Health" implies otherwise.
6. **`JwksCache` retries on every request when the key fetch fails**, so
   `MIN_REFETCH_INTERVAL_SECONDS` does not throttle the path it was written for.
   Caused a burst of confusing 401s right after a cold start.
7. **~400ms per round trip to the pooler** is inherent to this deployment
   (`DEC-006`: a laptop, not co-located infrastructure). Not fixable in code;
   only fewer round trips help. See ADR-010's addendum and T3-5.
8. **T3-1 — a real video provider — is still the only open roadmap item.** The
   EXP-005 hardware gate now passes (page file resized), but running and
   accepting FramePack has not been done, and it is image-conditioned only.

## 8. The rule this project keeps relearning

A green suite means the code does what its author expected. It says nothing
about whether the expectation matched reality.

This session produced three fresh examples. The Profile screen showed
"Not signed in" for a *failed request*, which looked identical to having no
session. A profile write persisted but read back empty, because `get_user`
never selected the new column. And a confident "migration 009 is not applied,
the backend cannot boot" turned out to be a type-exact check in the gate itself
being wrong. All three were found by running the real thing and reading the
actual output.

Where a doc and the code disagree, the code wins. Where the code and the live
system disagree, the live system wins.
